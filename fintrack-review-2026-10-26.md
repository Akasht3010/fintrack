# Fintrack Weekly Code Review - 2026-10-26

## Summary
Both repositories were reviewed: `fintrack` (Expo/React Native + TypeScript, Expo Router, React Query, Zustand) at commit `8a37d4c`, and `fintrack-backend` (FastAPI + SQLAlchemy + Pydantic v2, Postgres) at commit `0dd0ce4`. This is a mature, carefully-engineered fintech codebase — a prior review cycle (2026-09-15) closed several real security issues (account enumeration, tokens-in-URLs, idempotency, localStorage-on-web for tokens), and all of those fixes are still in place; no regressions were found. The backend's IDOR discipline, Decimal-only money handling, OAuth state/CSRF handling, and OTP implementation are all genuinely solid — no backend Critical was found this cycle. The headline concern is on the frontend: **logout does not clear the React Query cache and most query keys aren't scoped per user id**, which on a shared/multi-user device can show one user's real financial data (budgets, balances, net worth) to the next person who logs in, for up to the 5-minute `staleTime` window. A second theme worth tracking is OAuth login-CSRF (no client-side `state` verification on the Google sign-in callback) and a few sync-related race conditions (overlapping Gmail/SMS syncs, no rate limit on sync endpoints). Static analysis tooling (mypy, pytest, tsc, eslint) could not fully execute in this environment because `fastapi`/`sqlalchemy` and the frontend's `node_modules` are not installed here — see the Nits section for what ran (ruff, `npm audit`) and what didn't.

## Critical (P0) - fix before deploy

- **[fintrack/src/store/useUserStore.ts:25-43]** Logout never clears the React Query cache, and most query keys aren't namespaced by user id — stale financial data from the previous user can be shown to the next one on the same device.
  Why it matters: `logout()` clears the stored token and the cached `"user"` blob, but never touches the `QueryClient` created in `app/_layout.tsx:26-33` (no `queryClient.clear()`/`removeQueries()`, and the client isn't even reachable from the store). Most screens' query keys have no user id in them at all: `["budgets"]` (`app/(tabs)/budget.tsx:31`, `app/(modals)/add-budget.tsx:23`), `["insights"]`/`["recurring"]` (`app/(tabs)/insights.tsx:27,32`), `["accounts"]`/`["net-worth"]` (`app/(modals)/accounts.tsx:39-40`), `["categories"]` (`app/(modals)/categories.tsx:26,36,135`). Only the transactions list/detail queries include `user?.id`. On a shared device, User A logs out and User B logs in without a full page reload (this is routine on the web build): with `staleTime = 1000 * 60 * 5` (`app/_layout.tsx:30`), User B's dashboard, budget, accounts, and insights screens can render User A's real budgets, account balances, and net worth before the first refetch completes — a direct cross-user financial-data leak in a money app.
  Fix:
  ```ts
  // src/store/useUserStore.ts — accept the QueryClient (e.g. via a setter called
  // once from app/_layout.tsx, or lift logout() into a hook that has access to
  // useQueryClient()) and clear it as part of logout:
  logout: async (queryClient: QueryClient) => {
    try {
      await authApi.logout()
    } catch {
      if (usesCookieSession) await authApi.clearSession().catch(() => {})
    }
    await clearStoredSession()
    await SecureStore.deleteItemAsync("user")
    queryClient.clear()               // <-- drop every cached query, not just auth state
    set({ user: null, isAuthenticated: false, isLoading: false })
  }
  ```
  Also namespace every per-user query key by `user.id` the same way `transactions` already does (`["budgets", user?.id]`, `["accounts", user?.id]`, `["insights", user?.id]`, etc.) as defense-in-depth even after the cache-clear fix, so a partially-stale cache can never cross a user boundary again.

## High (P1) - fix this sprint

- **[fintrack/src/utils/storage.ts:10-33]** Full user profile (name, email, phone) is persisted in plaintext `window.localStorage` on web, not just the access token.
  Why it matters: the prior cycle's "move off localStorage" fix only special-cased the `"access_token"` key (via `session.ts`, which skips storage entirely on web). The generic `storage` wrapper still falls back to `localStorage` for *any other* key on web, and the `"user"` key goes through it from `app/_layout.tsx:83`, `app/auth-callback.tsx:41`, `app/gmail-callback.tsx:37`, `app/(auth)/verify-otp.tsx:62`, `app/(auth)/reset-password.tsx:76`, `app/(modals)/edit-profile.tsx:40`, `app/(tabs)/profile.tsx:72`, `src/hooks/useGoogleAuth.ts:78`, `src/hooks/useGmailConnect.ts:73`, `src/hooks/useGmailSync.ts:53`. Any XSS (a bad dependency, a malicious extension, one injected script) can read full PII straight out of persistent `localStorage`, independent of the HttpOnly-cookie protection already covering the token.
  Fix: route the `"user"` key through the same web-safe path as the token (keep it in memory / the Zustand store only on web, or at minimum `sessionStorage`), rather than the generic `localStorage`-backed wrapper.

- **[fintrack/app/auth-callback.tsx:36-44] <-> [fintrack-backend/app/utils/oauth_state.py:23-44]** OAuth login-CSRF: the Google sign-in callback accepts and exchanges any `code` in the URL with no client-side `state`/nonce check.
  Why it matters: the backend's server-side nonce (`create_state`/`consume_state`) correctly stops an attacker from *forging* the redirect target, but nothing on the client ties the resulting single-use `code` to *this device's* own flow. An attacker can start their own Google OAuth flow, capture the resulting `code` (or the full `fintrack://auth-callback?code=...` link / web URL), and get a victim to open it. `auth-callback.tsx` unconditionally calls `authApi.exchangeGoogleCode(code)` and signs the victim's device into the *attacker's* account — a classic login-CSRF. Because the exchange code shares the same 600-second TTL as the OAuth state nonce (`_STATE_TTL_SECONDS = 600` in `oauth_state.py:12`), that's also a 10-minute window during which a leaked/intercepted code (e.g. via Android custom-URL-scheme interception, since `fintrack://` isn't an exclusively-owned App Link) stays exchangeable — longer than an exchange code strictly needs to live.
  Fix: generate a random nonce client-side before navigating to `authorizeUrl` (both `useGoogleAuth.ts` and `useGmailConnect.ts`), persist it for the duration of the flow, and have the backend echo it back through `/callback` and `/exchange` for the client to verify before trusting the result. Independently, consider giving the exchange-code nonce its own short TTL (e.g. 60s) instead of reusing the 10-minute OAuth-state TTL.

- **[fintrack/app/(modals)/add-expense.tsx:64-75] <-> [fintrack/src/api/invalidate.ts:8-16]** The edit-transaction form can be silently overwritten mid-edit by an unrelated background sync.
  Why it matters: the edit-mode effect re-hydrates `amount`/`merchant`/`category`/`description` from `existing` every time that query object changes identity. `invalidate.ts` invalidates the `["transaction"]` prefix (matching the open `["transaction", id]` query) on every transaction write — including ones triggered by `useGmailAutoSync` or an SMS sync running in the background while the user is mid-edit. The effect then overwrites whatever the user has typed with the server's old values. On a money-entry screen, that's silent data loss, not just a UX glitch.
  Fix: seed the form state once (e.g. `useState(() => ...)` keyed off the id, or a "has the user touched this field" ref/dirty flag) instead of reactively re-hydrating on every `existing` change.

- **[fintrack/src/hooks/useGmailSync.ts:20-64] <-> [fintrack/src/hooks/useGmailAutoSync.ts:11-34]** Overlapping Gmail syncs aren't actually prevented.
  Why it matters: each `useGmailSync()` call site (`useGmailAutoSync`, mounted once in `app/_layout.tsx:98`, and `profile.tsx`'s own instance) keeps its own local `isSyncing` state — there's no shared lock. Two concurrent `gmailApi.sync()` calls (e.g. autosync firing right as the user taps "Sync Gmail Now") can run at once, each independently reading/writing budgets and firing its own budget-threshold-crossing notifications off different `budgetsBefore` snapshots, risking a double- or mis-fired alert. The same risk shape applies to `useSmsSync.ts` if it's ever called from two places.
  Fix: hoist the in-flight guard to module scope (a single shared `let gmailSyncInFlight: Promise<...> | null` all callers read/await) or route sync orchestration through one shared React Query mutation whose `isPending` is the single source of truth.

- **[fintrack-backend/app/api/sms.py:21] and [fintrack-backend/app/api/gmail.py:119]** No rate limit on the two most expensive endpoints.
  Why it matters: every sensitive auth endpoint in `app/api/auth.py` carries `@limiter.limit("10/minute")`, but `/api/sms/sync` and `/api/gmail/sync` don't. A single call to `/api/sms/sync` can carry up to `MAX_SMS_PER_SYNC=500` messages (`app/schemas/sms.py:8`), each costing a DB query + parse + commit; `/api/gmail/sync` additionally makes a live Gmail API call per sync. Nothing stops a compromised token or a buggy/retrying client from firing either repeatedly, burning Google API quota and hammering the DB continuously.
  Fix: add `@limiter.limit(...)` (e.g. 5-10/minute) to both routes, matching the pattern already used in `auth.py`.

- **[fintrack-backend/app/services/gmail_service.py:109-125] <-> [fintrack-backend/app/services/email_parser.py:145]** Gmail email body has no size cap before being run through regex parsing, unlike the SMS path.
  Why it matters: `get_email_body` returns the full decoded body with no length limit, which then flows straight into `parse_bank_email` (`app/api/gmail.py:170-175`), concatenated with subject/snippet and run through roughly 10 regex patterns per email, per sync. `app/schemas/sms.py:9` caps SMS bodies at `MAX_SMS_BODY_LENGTH = 2000` for exactly this reason, but the equivalent bound was never applied to Gmail — and email delivery has no auth boundary, so a spoofed "has been debited"-style email with an adversarially large body reaches this unbounded regex pass on every sync.
  Fix: truncate the decoded body (e.g. to 10-20 KB) before calling `parse_bank_email`, mirroring the SMS bound.

## Medium (P2) - worth doing

- **[fintrack-backend/app/services/budget_service.py:59-67,118-146]** Budget creation and period-rollover are check-then-insert with no DB-level backstop, unlike every other dedup path in this codebase.
  Why it matters: there's no unique constraint on `(user_id, category, period)` while active. Two concurrent requests (double-tap, two devices) can both pass the "no active budget yet" check and both insert, producing duplicate "active" budgets the UI then shows as doubled limits/spend. `roll_forward`, called on every `GET /api/budgets`, has the identical gap at period boundaries. `Transaction` already has partial unique indexes for exactly this race shape (`idx uq_transactions_user_raw_text`/`...idempotency_key`); `Budget` doesn't.
  Fix: add a partial unique index on `(user_id, category, period)` scoped to the active window, or wrap the insert in `try/except IntegrityError` the way `verify_email_change` (`app/api/auth.py:477-481`) already does.

- **[fintrack-backend/app/schemas/insights.py:7,11,15] <-> [fintrack/src/utils/money.ts:3-9]** Insights/recurring/admin totals cross the API as `float`, breaking the app's own "every amount is a decimal string" invariant.
  Why it matters: every ledger money column (`Transaction.amount`, `Account.opening_balance`, `Budget.limit_amount`) is `Decimal` end-to-end and serialized as an exact string via the shared `Money` Pydantic type (`app/schemas/money.py`) — specifically so the frontend's `Decimal`-based money helpers never have to parse a lossy JSON number. But `app/api/insights.py:59,87,109` and `app/services/recurring_service.py` cast `SUM()` results to `float` and type them as plain `float` in `MonthlyTotal.total`, `CategoryBreakdownItem.total`, `MerchantBreakdownItem.total`, `RecurringItem.average_amount`, and `RecurringSummary.monthly_total`. The frontend's own `money.ts` comment ("Every amount field from the API... travels as a decimal string") is simply false for these fields — they arrive as JSON numbers the Decimal-safe parsing path never gets a chance to run on. For aggregate spend/income numbers shown on the dashboard, this quietly reintroduces the float-precision risk the rest of the app was built to avoid.
  Fix: give these fields the same `Money` type (or at least serialize via `str(Decimal)`), keeping `SUM()` as `Decimal` all the way to the response.

- **[fintrack-backend/app/services/recurring_service.py:36-45]** `detect_recurring` loads a user's entire debit transaction history, unbounded, on every call.
  Why it matters: unlike `insights.py` (bounded to ≤12 months), this query has no date filter or limit — for a long-lived user it becomes an ever-growing full-table scan plus Python-side grouping on every `GET /api/recurring`, with no caching between requests.
  Fix: bound the query to a trailing window (e.g. 18-24 months), comfortably covering the weekly/monthly/yearly cadences `CADENCE_WINDOWS` detects.

- **[fintrack-backend/app/api/auth.py:502] and [fintrack-backend/app/api/gmail.py:111], [fintrack-backend/app/services/gmail_service.py:106,123]** `print()` instead of structured logging for operationally important failures.
  Why it matters: these are exactly the failures the code's own comments worry about going unnoticed ("a systematically broken revoke path would never surface anywhere"), but `print()` bypasses log levels and structured aggregation, making them easy to lose in production. Only `app/api/gmail.py:86,147` use the module `logger` correctly.
  Fix: route these through `logging.getLogger(__name__).warning/exception(...)`.

- **[fintrack/app/(tabs)/budget.tsx:46-54]** Budget delete has no error handling and no in-flight guard.
  Why it matters: every other delete flow in the app (`transaction-detail.tsx:46-55`, `accounts.tsx:67-71`, `categories.tsx:34-38`) wraps the call in try/catch with a user-facing alert on failure and disables the row while pending; this one does neither, so a failed delete throws an unhandled rejection with no feedback, and a rapid double-tap can fire two DELETE requests for the same row.
  Fix: wrap in try/catch + `showAlert`, and add a per-row `isDeleting` guard mirroring `accounts.tsx`.

- **[fintrack/app/(tabs)/transactions.tsx:41-73]** Min/max amount filters bypass the debounce the search box uses, firing a request per keystroke.
  Fix: debounce `minAmount`/`maxAmount` the same way `debouncedSearch` already is.

- **[fintrack/app/_layout.tsx:106-132]** Possible flash of protected content (combined with the P0 cache issue, a *previous user's* content) on web before the auth guard redirects, since the `<Stack>` renders unconditionally while `checkAuth()` is still in flight and the splash screen doesn't cover web.
  Fix: gate rendering on `isLoading` (show a neutral loading view) rather than mounting the full navigator immediately.

- **[fintrack/src/api/client.ts:162-193]** Every 403 (and non-whitelisted 401) is treated as "session expired" and forces a logout, on a convention ("the app never uses 403 for anything else") rather than a contract.
  Why it matters: any future domain-specific 403 (e.g. a permission check on a shared resource) would silently log the user out with a misleading "session expired" message instead of surfacing the real error.
  Fix: have the backend use a distinct error shape/code for non-auth 403s, or scope this handling to a known allowlist of protected paths instead of "everything except this exclude-list."

- **[fintrack-backend/app/services/category_service.py:64-73] and [fintrack-backend/app/api/auth.py:397-400]** Two uniqueness checks (category name, phone number) are check-then-insert without catching the DB constraint's `IntegrityError`, unlike the equivalent email-change path (`auth.py:477-481`) — a concurrent duplicate 500s instead of cleanly 409ing.
  Fix: wrap both commits in `try/except IntegrityError` the same way.

## What looks good
- **IDOR discipline is consistently correct.** Every single-object read/write on transactions, accounts, budgets, and categories scopes to the owning `user_id` in the same query that fetches the row — verified across all of `transactions.py`, `accounts.py`, `budgets.py`, `categories.py`, including re-validating account ownership on transaction create/update (`_ensure_account_owned`). This is the single most important thing to get right in a personal-finance app and it holds everywhere checked.
- **Money handling is rigorous end-to-end for the actual ledger**: `Numeric(12,2)`/`Decimal` columns, a shared `Money` Pydantic type that serializes as an exact string specifically to avoid float drift, a boot-time migration that actively hunts down and fixes lingering `FLOAT` columns, account balances always derived via `SUM()` on read (no stored balance to desync), and a matching `decimal.js`-based parser/formatter on the frontend with real regression tests for repeated-addition float drift.
- **OAuth state handling and redirect allowlisting are excellent**: a random server-side nonce (never a client-decodable payload), stored only as its hash, single-use via delete-rowcount (closing a race between concurrent consumers), short TTL with pruning, and a genuine allowlist (not a reflection) for `app_redirect_uri`.
- **Auth internals are solid**: bcrypt password hashing, `hmac.compare_digest`/atomic conditional `UPDATE` for OTP comparison and attempt-limiting (closing a concurrent-guessing race), `token_version` bump on password reset to invalidate every outstanding session, and admin routes gated by a genuinely distinct API-key dependency with its own rate limit — not just `get_current_user` again.
- **CORS, CSV-injection, and dev-mode secret hygiene are all deliberately handled**: explicit origin allowlist (never `*` with credentials), formula-injection-safe CSV export, and OTP codes refuse to print to logs unless `ENV` is explicitly `"development"` (defaulting to the strict production behavior if unset).
