# Fintrack Weekly Code Review - 2026-11-02

## Summary
Both repos are in good shape and show an unusually mature, deliberately-hardened approach to fintech basics: money is `Decimal`/`NUMERIC(12,2)` end-to-end on the backend and parsed with `decimal.js` on the frontend, IDOR ownership checks are applied consistently on every transaction/account/budget/category handler, and auth/session handling (bcrypt, `token_version` revocation, atomic OTP reservation, DB-bound single-use OAuth state, enumeration-safe login) is far ahead of what a typical personal-finance side project ships with. The one real security-adjacent issue is on the frontend: logout doesn't clear the React Query cache or the transaction store, so a previous user's financial data can briefly render for the next person who logs in on the same device. Reviewed `fintrack` at commit `8a37d4c9d34bf445a51304b3212c502b29e55a84` and `fintrack-backend` at commit `0dd0ce4a66645cc14f42570fef2e1518ee99d7de`; both repos were available and fully reviewed. Static-analysis tools that require installed dependencies (mypy, pytest, pip-audit, `expo lint`, `tsc`) could not run in this environment because neither repo's dependencies are installed and installing them was out of scope for this review — see **Nits & style** for what did run (`ruff`, `npm audit`) and a manual secret scan (clean).

## Critical (P0) - fix before deploy
- **[fintrack: app/_layout.tsx, src/store/useUserStore.ts:25-43]** Logout doesn't clear the React Query cache or the transaction store, so a previous user's financial data can render for the next logged-in user on the same device.
  Why it matters: `useUserStore.logout()` clears the token/cookie and the user store, but the app's single module-level `QueryClient` (created in `app/_layout.tsx`) and `useTransactionStore` are never reset. On a shared or handed-off device (a family tablet, a device passed to support, a quick account switch), a second account signing in immediately after sees the first user's cached transactions, budgets, accounts, and insights flash on screen until each query refetches. That's a direct cross-user financial-data and PII leak — exactly the class of bug this review's fintech bar exists to catch.
  Fix:
  ```ts
  // src/store/useUserStore.ts
  import { queryClient } from "@/api/queryClient" // lift the QueryClient out of app/_layout.tsx into its own module

  logout: async () => {
    // ...existing token/cookie clearing...
    queryClient.clear()
    useTransactionStore.getState().reset() // add a reset() action that zeroes transactions/summary/loading/error
    set({ user: null, isAuthenticated: false })
  }
  ```

## High (P1) - fix this sprint
- **[fintrack: src/utils/storage.ts, called from useGoogleAuth.ts:78, app/(auth)/auth-callback.tsx:41, app/(auth)/gmail-callback.tsx:37, useGmailSync.ts:53]** The full `user` object (name, email, `gmail_connected`, avatar) is cached via `SecureStore.setItemAsync("user", JSON.stringify(user))`, and on the web build `SecureStore` is a thin wrapper over `window.localStorage` — unlike the access token, this cache is never gated behind `usesCookieSession`.
  Why it matters: this is PII sitting in plaintext browser storage for the lifetime of the session (and after a crash/non-graceful close), readable by any XSS or malicious browser extension on the page — exactly the attack surface the project's own "no JWT in localStorage" convention was designed to close for the token, just reopened for the profile object instead.
  Fix: hold `user` only in the in-memory `useUserStore` on web (refetch via `GET /api/auth/me` on load) instead of persisting it to `storage`, or if a cache is needed, strip it to a non-PII shape (e.g. just a boolean "has a session").

- **[fintrack-backend: app/utils/admin_auth.py:14-15]** `@limiter.limit("30/minute")` is applied to `require_admin_key`, a shared FastAPI dependency, rather than to each admin route individually, and slowapi commonly keys/labels a limit bucket per matched route.
  Why it matters: if slowapi does bucket per-route here, `/api/admin/health` and `/api/admin/stats` each get an independent 30/min allowance instead of sharing one 30/min budget — quietly doubling the effective brute-force budget against `ADMIN_API_KEY`. This could not be confirmed in this environment (slowapi isn't installed), so treat as "verify, likely fix" rather than confirmed.
  Fix: add a test that hits `/api/admin/health` 30 times then immediately hits `/api/admin/stats` once and asserts a 429, or switch to an explicit shared rate-limit key (e.g. `key_func=lambda request: f"admin:{client_ip(request)}"` scoped once, independent of route) so all admin traffic shares one bucket per caller.

- **[fintrack-backend: requirements.txt:19]** `python-multipart==0.0.6` is pinned below 0.0.9, which fixed a multipart-boundary ReDoS (GHSA-qgvh-v25w-33v4).
  Why it matters: FastAPI's form/file-upload parsing depends on this package; a crafted multipart body to any endpoint that accepts form data can cause excessive CPU — a real availability risk on a single-instance deployment (the app is already pinned to `--max-instances=1` per `cloudbuild.yaml`).
  Fix: bump to `python-multipart>=0.0.9` in `requirements.txt` and smoke-test any multipart-consuming endpoint.

## Medium (P2) - worth doing
- **[fintrack-backend: app/schemas/budget.py:9,16]** `BudgetCreate`/`BudgetUpdate.limit_amount: Money = Field(gt=0)` has no upper ceiling, unlike `TransactionBase.amount` (`le=MAX_TRANSACTION_AMOUNT`) and `AccountCreate.opening_balance` (`le=MAX_OPENING_BALANCE`). Fix: `limit_amount: Money = Field(gt=0, le=MAX_TRANSACTION_AMOUNT)` (import the constant from `app.schemas.transaction`).
- **[fintrack-backend: app/services/account_service.py:78-82]** `AccountService.create(db, user_id, name, type, currency, opening_balance)` takes `currency` as a parameter but the body hardcodes `currency="INR"`, silently discarding whatever the caller passed. Fix: either drop the dead parameter, or make `AccountCreate.currency: Literal["INR"]` so a non-INR value 422s instead of being swallowed.
- **[fintrack-backend: app/services/otp_service.py:60-70]** The 30s OTP resend cooldown is a read-then-insert with no locking — two near-simultaneous requests can both see "no recent unconsumed OTP" and both insert, each emailing a code and bypassing the cooldown once. Low impact (the per-route rate limiter bounds real damage), but inconsistent with the atomic `UPDATE ... WHERE` pattern this same file correctly uses for attempt-reservation and consumption. Fix: a unique partial index on `(user_id, purpose) WHERE consumed = false`, or wrap check+insert in `SELECT ... FOR UPDATE`.
- **[fintrack-backend: app/api/auth.py:187-193]** `/signup` returns a distinct 409 for "email already exists" vs. "phone already exists," letting a caller enumerate registered emails/phones — notable because the rest of this module (login, forgot-password) goes out of its way to avoid exactly this leak via a dummy-hash timing match. Fix: either accept the UX trade-off explicitly (document it) or return one generic "an account with this email or phone already exists" 409.
- **[fintrack: app/(modals)/add-expense.tsx:80-84, app/(modals)/accounts.tsx:216-223]** No client-side max-amount ceiling before submit — only format and positivity are checked. A user who types an absurd amount gets a raw 422 round trip instead of an inline message. Fix: mirror `MAX_TRANSACTION_AMOUNT`/`MAX_OPENING_BALANCE` as frontend constants and validate before the network call.
- **[fintrack: app/(modals)/add-expense.tsx:196-214]** The Debit/Credit type toggle (and the category/account `Chip` selections) has no `accessibilityRole`/`accessibilityState={{selected}}`, even though it directly determines transaction direction — missed by the otherwise-thorough a11y pass that covered the Amount/Merchant fields and submit button. Fix: add `accessibilityRole="button"` and `accessibilityState={{ selected: transactionType === t }}` to the toggle (and `Chip`).
- **[fintrack-backend: Dockerfile]** No `USER` directive — the container runs as root inside Cloud Run. Low real-world risk given Cloud Run's sandboxing, but worth defense-in-depth. Fix: `RUN useradd -m appuser` + `USER appuser` before `CMD`.

## Cross-repo contract issues
- **[fintrack: src/api/endpoints/transactions.ts:5 (`TransactionCreatePayload.amount: number`), budgets.ts:4-8 (`limit_amount: number`), accounts.ts:16 (`opening_balance?: number`) <-> fintrack-backend: app/schemas/money.py (`Money` serializes as a JSON *string* on every read)]** Money fields are asymmetric across the wire: every response (`Transaction.amount`, `Account.balance`, `Budget.limit_amount`, etc.) is typed and documented as a decimal *string* on the frontend (`src/types/domain.ts`), but every write sends a raw JS `number`. What breaks: nothing today — `parseMoneyInput` caps input at 2 decimal digits and Pydantic's float→Decimal coercion round-trips exactly at these magnitudes — but it's a landmine the money.py docstring explicitly warns against ("a JSON number is a float on every consumer... inviting client-side float arithmetic"), and it would silently reintroduce precision loss if anyone later does arithmetic on the parsed value before sending or the amount approaches float-precision limits. Fix: send the validated decimal string directly in create/update payloads instead of a `number`.
- **[fintrack-backend: app/schemas/insights.py, app/schemas/recurring.py (`float` fields) <-> fintrack: src/types/domain.ts (`MonthlyTotal.total: number`, `RecurringItem.average_amount: number`)]** `InsightsSummary`/`RecurringSummary` use raw `float`, not the shared `Money` Decimal-as-string type every other money field in this API uses. The frontend correctly mirrors this as `number`, so there's no frontend bug, but it means two different "amount" wire representations coexist in one API, which is confusing and risks drift if these totals are ever compared against or combined with ledger amounts elsewhere. Fix: move these fields onto `Money` for consistency (they're sums of `Numeric(12,2)` columns already, so no new precision is introduced).
- **Verified, no finding — field names, routes, and error envelope.** Every route path and HTTP method registered in `fintrack-backend/app/api/*.py` has a matching call in `fintrack/src/api/endpoints/*.ts` (and vice versa — no dead backend endpoints, no 404-prone frontend calls found). Request/response field names are snake_case on both sides with zero camelCase drift. The error envelope is handled consistently: `extractErrorMessage` (`src/api/client.ts:32-46`) normalizes both FastAPI's plain `{"detail": "..."}` string and Pydantic's 422 `{"detail": [{loc,msg,type}]}` array shape into one readable message.
- **Verified, no finding — timestamps.** The backend deliberately stores every business timestamp as naive IST wall-clock (no UTC "Z" suffix) — documented in `app/utils/timezone.py` — and the frontend's `src/utils/date.ts` correctly parses with `dayjs.tz(date, "Asia/Kolkata")` rather than assuming device-local time or UTC. This is a deliberate, consistently-documented deviation from plain ISO 8601-with-offset, correctly implemented on both sides, not a bug.
- **Verified, no finding — auth transport.** The Bearer-vs-cookie branch (`fintrack/src/utils/session.ts`, `src/api/client.ts`) matches what the backend's `get_current_user` expects on each transport, including the `X-Auth-Transport` CSRF header check confirmed by the backend auth review.

## Nits & style
- `ruff check .` on fintrack-backend: 254 findings, mostly low value — 81 `B008` (FastAPI's `Depends()`-in-default-argument idiom, a well-known false positive for this framework), 67 `UP045` (`Optional[X]` vs `X | None` style), 36 unsorted imports, 30 verbose `Decimal("10")` constructor nits. 149 are auto-fixable with `ruff check --fix .`; worth a cleanup pass but none are correctness bugs.
- `mypy`, `pytest --collect-only`, and `pip-audit` could not run on fintrack-backend: FastAPI/SQLAlchemy aren't installed and there's no virtualenv in this environment; installing dependencies was out of scope for a review-only run, so these were skipped rather than worked around.
- `npm run lint` and `npx tsc --noEmit` could not run meaningfully on fintrack: `node_modules` isn't installed in this environment, so `expo` isn't on PATH and every import resolves as "module not found" — not real type errors, just missing dependencies. Skipped for the same reason as above.
- `npm audit --omit=dev` on fintrack: reported 54 vulnerabilities (1 critical: `shell-quote` ReDoS; several high: `node-forge`, `source-map-js`, `zod`) — all are transitive dependencies of the Jest/Metro/Babel toolchain or deep React Native tooling, not reachable from the shipped app bundle. Worth a periodic `npm audit fix` pass, not urgent for production risk.
- Secret scan (hardcoded API keys, AWS keys, private key blocks) across both repos: clean. The only `.env*` file found is `fintrack-backend/.env.example`, which contains placeholder values only (`change-me`, `your-app-password`, etc.), no real secrets.
- `fintrack-backend/app/config/init_db.py`: several `except Exception: print(...)` migration guards on DDL statements are intentional and well-commented (pre-existing duplicate data shouldn't block startup), but they only surface via Cloud Run logs, not structured logging/alerting — a silently-never-created index would be easy to miss.

## What looks good
- Money is `Numeric(12,2)`/`Decimal` end-to-end on the backend, serialized as JSON strings (never floats) via a single shared `Money` type, and the frontend consistently parses with `decimal.js` and one `Intl.NumberFormat("en-IN")`-based formatter — zero hardcoded `$`/`toFixed(2)`-on-float call sites found anywhere in either repo.
- IDOR discipline is excellent and consistent: every read/write handler for transactions, accounts, budgets, and categories filters by `user_id` at the query level (never fetch-then-check), and nothing anywhere trusts a client-supplied user id.
- Auth/session hardening is unusually mature for a project this size: bcrypt hashing, a `token_version` column giving real "log out everywhere" semantics, atomic `UPDATE ... WHERE`-based OTP attempt-reservation and consumption, DB-bound single-use OAuth state (closing both CSRF-via-state and open-redirect/token-leak vectors), and login/forgot-password responses that are deliberately indistinguishable for unknown accounts, wrong passwords, and Google-only accounts (including a dummy-bcrypt-hash timing match).
- Idempotency is enforced at the database layer (partial unique indexes on `(user_id, idempotency_key)` / `(user_id, raw_text)`), not just an app-level check — correctly closing the retry/duplicate-insert race for manual entry and for the Gmail/SMS import paths alike.
- Cross-repo alignment (field names, route paths, error envelope, timestamp convention) is clean, with no drift found anywhere in this review — a sign the two repos are being kept in sync deliberately rather than by luck.
